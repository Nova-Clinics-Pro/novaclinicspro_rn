## 2. Naming-convention findings (verified, not assumed)

- **Resource names:** singular. One exception: `reports` (`reports.view`).
- **Separator:** dot between resource and action (`resource.action`); underscore inside multi-word resource names (`treatment_sheet`, `treatment_order`, `treatment_session`, `treatment_proposal`, `clinical_service`, `staff_leave`, `staff_document`).
- **"finalize" vs "finalise":** **neither spelling exists anywhere** in permission or RBAC-adjacent code. `casesheet.finalise` as proposed would be the first use of either spelling in this vocabulary — another reason it is not simply added by pattern-matching (see row 2 above).
- **"Treatment sheet" vs "treatment session":** **both are real, independently-permissioned resource namespaces**, plus two more: `treatment_order` (scheduling worklist) and `treatment_proposal` (pre-Plan recommendation stage), plus a fifth generic `treatment.read`/`treatment.update`. **R7's "Treatment Recommendation → Plan → Sessions" model must map onto this existing five-namespace reality**, not a single "treatment" resource. This is directly relevant to design.md §2.3/§2.8 and should inform `T-BE-D.1`'s domain modelling — recorded here as an ETX finding, not acted on.
- **Invoice vs billing:** only `invoice.*` exists in the enforced catalog. `billing.*` exists solely in the dormant System A enum. The frontend feature folder is named `features/billing/` — a vocabulary mismatch across the stack, not a blocking issue, but worth the owner's awareness for `T-BE-F.1`/`T-FE-E.4` naming choices.
- **No generic `clinical_document` permission** unifying case sheet/prescription/treatment sheet exists — each document type is independently permissioned, consistent with R7's principle of one meaning per document type.
- **No single broad permission unifies create+sign for any document type.** The opposite problem exists instead: sign-specific codes are seeded but **unenforced** (see rows 3 and 6).

If true at runtime, those six migrations' grants silently insert zero rows (the subquery returns no match) rather than erroring — a silent, not loud, gap. **This was not checked against a live database in this task** (out of scope for the 16-code question, and this task performed no DB access at all, read-only or otherwise). Recommend a dedicated read-only check before any task that assumes `CLINIC_ADMIN`/`CLINIC_OWNER` permission grants are live (this may affect `T-FE-E.6` role/capability composition and any task assuming admin-level R7 permissions exist today).

## 4. Capability vs. permission — no conflation found

Capabilities (`org_capabilities`, e.g. `appointments.multiday`) are a structurally separate table/model from `org_permissions`, explicitly documented as never mutated by a runtime write path. `require_capability_available()` (`app/api/v1/dependencies/capability_guard.py`) exists but **is not called by any router found** — dead/unwired on this branch, not evidence of conflation. The R5 capability-permissions migration's own docstring states the two concerns are "independently-owned, composed concerns, never merged into one check" — confirmed by absence of any counter-example. **No conflation exists in the code searched.**

## 5. Frontend-only enforcement — one real finding, correctly scoped

`episodeWorkspaceConfigByRole` (`features/episodes/presentation/config/episodeWorkspaceConfig.ts`) gates Visit Notes editing, "New Prescription," and Treatment Sheet create/schedule CTAs by a `mode` value that comes from a **URL query parameter** (`app/clinic-admin/episodes/[episodeId]/workspace.tsx:15-23`), not from the authenticated user's actual role — `?mode=doctor` (or its default) shows doctor CTAs to anyone. **However**, every underlying write action this gates (`prescription.create`, `treatment_sheet.create`, `treatment_order.schedule`, `casesheet.update`) **is independently backend-enforced** (cited in the table above and §1). So this is a **UI defense-in-depth gap** (a confusing/misleading front-end experience for the wrong role), **not an unenforced-action gap** — the backend cannot be bypassed by manipulating the URL. Recorded, not fixed. Relevant to `T-FE-E.6` (role/capability composition), which already targets this exact file.
