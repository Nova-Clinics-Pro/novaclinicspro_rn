## Engineering Truth: the current violation, confirmed

`features/episodes/presentation/pages/CompleteConsultationScreen.tsx` →
`deriveSummary(data, appointmentId, includeAyurveda)`:

- Composes a `ConsultationSummary` (notes / prescription / treatment
  recommendation / Ayurvedic assessment) entirely client-side from
  `EpisodeWorkspaceData` (`useEpisodeWorkspaceData`, itself architecturally
  clean — governed repository hooks only, no datasource/axios import).
- `treatmentSent = treatmentState != null && treatmentState !== 'DRAFT'` —
  re-derives the treatment order's execution lifecycle locally, duplicating
  backend semantics the R4 `treatment_lifecycle_resolver` already owns
  (`lifecycle_status`/`lifecycle_status_label`). The function's own comment
  records this derivation was already once wrong (read `status` instead of
  `state`).
- `hasAyurveda` hard-codes clinical template IDs `['nadi_pariksha',
  'prakriti']` and inspects raw `casesheet.data_json.extensions` JSON to
  decide whether an Ayurvedic assessment was performed.
- Missing/absent data renders as a definitive negative clinical statement:
  `'Not saved'`, `'Not created'`, `'Not sent'`, `hasAyurveda === false`.
- `complete()` calls `transitionCasesheetStatusApi(tenantId,
  summary.casesheetId, { status: 'FINAL' })` **directly from the datasource
  layer** — a Case Sheet finalization decision made from local derivation,
  with the only precondition being `!!summary.casesheetId` (no readiness
  check of any kind).

This exactly matches `ENGINEERING-DEBT.md`'s own `ED-ARCH-004` entry
(`.kiro/engineering/ENGINEERING-DEBT.md:203-221`, backend repo), which
records this as a **ratified, known gap** — "Do not fix during
documentation" — not a new finding.

## Why Path C (a frontend-only transitional safe state) was not used

T-0.8's task text offers Path C — "disable or defer the final completion
action with an explicit, localized unavailable state" — **only if the task
plan permits a transitional safe state**. It does not, here:

- The approved AC (above) is written unconditionally in terms of rendering
  *the backend contract*, not a frontend-invented fallback state.
- `tasks.md`'s own Rollback note for T-0.8 (*"flag `cos_v1` off restores
  the legacy screen (never deleted in R7)"*) and for T-BE-F.3 (*"FE falls
  back to flag-off legacy screen"*) describe a **target** architecture:
  T-0.8 is expected to introduce a **new**, flag-gated implementation that
  renders the T-BE-F.3 contract, with the *current* screen serving as the
  flag-off legacy fallback. **No `cos_v1` flag exists anywhere in the
  frontend codebase today** (verified: zero matches for `cos_v1` across the
  repository) — this flag is part of T-0.8's own undelivered scope, not a
  pre-existing mechanism T-0.8 can lean on.
- This session's own governing instruction for T-0.8 explicitly prohibits
  adding a new feature flag "unless an existing completion-route flag
  already governs the whole path" — none does.
- `T-FE-F.2` (`tasks.md:469-470`, the task that actually retires this
  screen) is itself gated on **both** T-0.8 and T-BE-F.3, confirming the
  plan's own sequencing: no interim frontend-only milestone is defined
  between "violation as it stands today" and "backend contract exists."

Inventing an ad-hoc interim state (e.g., a locally-composed "Unavailable"
summary, or a client-side readiness gate) would itself be exactly the
prohibited pattern T-0.8 exists to remove — a new frontend-derived
interpretation of clinical readiness, just phrased as "unavailable" instead
of "not sent." That is not authorized by the frozen design.
