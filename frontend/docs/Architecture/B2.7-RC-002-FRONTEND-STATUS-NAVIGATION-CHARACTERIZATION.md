## Historical frontend trace

`Index` obtains the authenticated user's identifier from `useAuth`, calls
`useRegistrationStatus(userId)`, and uses the repository/use-case/datasource
chain to request `/api/v1/auth/registration-status/{userId}`. The root then
uses `resolveRegistrationStatusRoute`:

```text
pending_review -> /onboarding/pending-review?applicationId=…
rejected       -> /onboarding/rejected?applicationId=…
approved + tenant_id / onboarding + tenant_id
               -> /onboarding/setup-wizard?tenantId=…
approved without tenant_id -> /onboarding/choice?applicationId=…
draft          -> /onboarding/draft?applicationId=…
```

The pending and draft screens refresh status then return to the root gate. The
baseline rejected screen has no self-service retry/resubmission path. Loading
is owned by the root query gate. No frontend test proves backend authorization.
