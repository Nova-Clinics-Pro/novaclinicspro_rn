## 2026-10-13 owner clarification: minimum safe operational readiness

NovaClinics is pre-MVP and has no commercial customers. The target product has
one commercial-neutral workspace-provisioning model: registration, approval,
and workspace provisioning never start commercial time.

Minimum safe operational readiness is the eligibility gate for an authorized,
explicit 30-day commercial-trial activation. Optional clinic configuration may
continue during that active trial. A readiness result is commercially
`ELIGIBLE`; it is never itself a commercial activation. The exact
capability-aware checklist remains governed by existing approved readiness and
capability requirements. A missing concrete prerequisite is a
`PRODUCT_DECISION_REQUIRED`, not an invitation to make optional setup mandatory.

This clarification supersedes the prior *assumption* of existing commercial
customer cohorts. It does not authorize destructive cleanup, automatic
conversion, recreation, or deletion of actual development or test records. Any
such records remain technical-compatibility evidence and require separate
classification before a migration or cleanup proposal.

## Independent lifecycle contracts

### 1. Registration and approval

- Public self-registration is a supported product entry path.
- Contact ownership verification is mandatory before an automatic-approval path
  can be used.
- Automatic approval is permitted only when explicitly approved
  automatic-verification and approval criteria are satisfied. PF-018 governs
  verification-evidence authority; it does not by itself create a registration
  approval threshold.
- A registration not meeting those criteria follows the existing appropriate
  review path; it is not silently rejected, approved, or provisioned by a
  fallback rule created in implementation.
- Exact application enum names, review queues, and risk rules are implementation
  details unless separately approved.

### 2. External identity reconciliation

- Authentication is the authority for external identity creation and external
  identity truth.
- The local lifecycle must durably represent an incomplete external operation,
  its correlation identity, and its reconciliation disposition.
- Best-effort deletion of an external identity can be a compensating action but
  is never the sole correctness guarantee.
- No external-provider call is required to succeed while a local database
  transaction is open. Retries reconcile the recorded phase; they do not replay
  a completed local mutation as a new registration.

### 3. Workspace provisioning and recovery

- Approval is a product decision and remains valid after a technical
  provisioning failure.
- Provisioning success establishes a valid workspace; only then may downstream
  tenant-scoped readiness and operational access be evaluated.
- A recoverable failure records a safe status and recovery information, does
  not claim workspace success, and does not imply readiness.
- Recovery must reuse the original authoritative command identity and must not
  recreate a tenant merely because a prior operation is ambiguous.

### 4. Readiness and commercial entitlement

- Readiness is a backend-authoritative eligibility projection over a valid
  workspace. It is not an approval flag, provisioning-success flag, or
  commercial entitlement.
- A ready clinic becomes commercially `ELIGIBLE`; it does not begin a trial.
- An authorized explicit Start Trial operation creates the new-E8 30-day
  commercial `ACTIVE` lifecycle under E8 authority.
- Optional configuration must not block eligibility unless an existing approved
  capability/readiness rule makes it necessary for safe operation.
- No commercial trial is inferred from registration, approval, provisioning, or
  readiness. Existing technical records must be classified before any cleanup
  or migration; no trial is recreated, converted, or inferred from technical
  provisioning state.

## State handoff invariants

The following semantic transitions are allowed. Storage representation and enum
names remain an implementation design decision.

| From | Event | To | Invariants |
| --- | --- | --- | --- |
| Registration intent | verified automatic criteria or review submission | approved path or review path | Contact evidence and actor/correlation facts are durable. |
| Approved application | provisioning command | workspace provisioned or recoverable provisioning failure | Approval survives failure; no readiness or tenant-operation success is reported on failure. |
| Recoverable provisioning failure | authorized recovery using original command identity | workspace provisioned or still recoverable failure | No duplicate tenant, membership, role seed, audit fact, or identity side effect. |
| Valid workspace | backend readiness evaluation | not-ready or commercially eligible | Readiness does not mutate commercial lifecycle. |
| Commercially eligible | explicit authorized Start Trial | commercial active | One clinic-scoped commercial clock; E8 authority and idempotency apply. |
| Any legacy cohort | governed classification/reconciliation | preserved legacy term or explicit reviewed mapping | No automatic tenant recreation, trial conversion, or entitlement reset. |

Forbidden transitions include:

- provisioning failure -> reported workspace success or readiness;
- approval -> unrestricted tenant clinical/operational access without a valid
  workspace and authorization context;
- readiness -> commercial active without explicit authorized activation;
- a retry -> a new tenant, identity, commercial trial, or completed replay;
- an ambiguous legacy record -> automatic repair or commercial conversion.

## Transaction, audit, and idempotency contract

### Local transaction boundary

The lifecycle is deliberately three durable local transactions, because a valid
approval must survive a technical provisioning failure:

1. **T1 — registration and approval:** one explicit application UoW persists
   the local applicant/application facts, a valid approval decision when one is
   authorized, a provisioning-intent/recovery record, and audit/outbox facts.
2. **T2 — workspace provisioning:** a separate explicit application UoW locks
   the application and provisioning record, then atomically creates the tenant,
   initial organization context, owner membership, RBAC/roles,
   application-to-tenant association, provisioning-success state, and
   audit/outbox facts. The provisioning core may flush but never commits.
3. **T3 — failure recovery:** after T2 rolls back, a separate UoW re-reads the
   durable command state. It records a safe recoverable or operator-required
   outcome only when the prior commit outcome is known. An unknown commit
   outcome is reconciled before any retry or failure record is written.

Each UoW has one top-level commit/rollback owner. Repositories and the
provisioning core only flush. After T2 commits, metadata synchronization,
session projection, notifications, and external-identity reconciliation are
retryable post-commit phases. Their failure cannot rerun completed local
workspace creation.

### Approved B1 recovery-persistence direction

B1 uses a separate, additive recovery aggregate rather than overloading the
business-approval lifecycle. The proposed table is
`org_tenant_application_provisioning_recoveries` with one row per application:

| Field | Purpose |
| --- | --- |
| `id` | Stable UUID primary key. |
| `tenant_application_id` | Required unique foreign key to the authoritative application. |
| `operation_id` | Required unique server-owned provisioning-command identity. |
| `state` | `pending`, `provisioning`, `succeeded`, `recoverable_failure`, or `operator_required`; it expresses technical recovery only. |
| `attempt_generation` | Monotonic attempt number, incremented only by an authorized retry of the same operation. |
| `correlation_ref` | Safe server-owned correlation reference for B2 identity reconciliation and audit. |
| `tenant_id` | Nullable successful workspace reference, set only with committed T2 success. |
| `safe_error_code` | Nullable non-secret failure classification; raw provider/database details remain in protected logs. |
| `created_at`, `updated_at`, `last_attempt_at`, `succeeded_at` | Durable timing and recovery evidence. |

T2 locks the application and recovery row in that order. A retry first reads
the locked durable result: `succeeded` replays the original result; an
unresolved or in-progress outcome is reconciled before mutation; an authorized
recoverable failure begins the next generation. A unique application key,
unique operation identity, application-to-tenant uniqueness, and existing RBAC
uniqueness constraints collectively prevent duplicate workspaces and owner-role
assignment. The recovery row, audit/outbox fact, and T2 local mutations commit
or roll back together.

This is a schema proposal, not an authorization to create a migration. B2 owns
public idempotency and external-identity reconciliation; B3 owns its safe
status projection; B4 owns readiness/commercial behavior.

### Public pre-organization idempotency

Public registration must have an explicit, server-authorized pre-organization
scope. It must include a stable subject/correlation identity, operation, key,
and a normalized request fingerprint sufficient to distinguish safe exact replay
from key reuse with changed material input.

The exact issuer of the pre-organization subject, persistence table shape,
retention duration, and key transport are engineering design details. They must
not use a placeholder tenant, a nullable scope ambiguity, raw client-provided
organization authority, or a client-chosen cross-applicant scope.

Required semantics are:

- atomic claim before side effects;
- stable in-progress outcome for same-scope concurrency;
- exact completed replay with no repeated domain or external effect;
- conflict for materially different command payload under the same scope/key;
- retryable reclamation only for the original authorized scope and fingerprint;
- tenant and applicant isolation in all replay/status reads.

## Authentication, authorization, and partial-state access

- Anonymous callers may begin only the public registration operation and cannot
  read another applicant, tenant, replay record, or recovery detail.
- An authenticated applicant may read their own registration/provisioning
  projection and only safe recovery information.
- Tenant clinical and operational endpoints require both a valid workspace and
  existing tenant authorization; application approval alone grants neither.
- Organization and tenant identity remain backend-authoritative. The frontend
  may present status, navigation, and retry affordances but never synthesizes
  provisioning, readiness, commercial, or authorization truth.

## Acceptance criteria and required evidence

An eventual implementation must provide evidence for all of the following:

1. Public registration supports verified automatic and review-path outcomes
   without invented criteria.
2. Approval persists across an injected local provisioning failure, while no
   workspace/readiness success is reported.
3. One UoW commits local registration/provisioning results once; failure rolls
   back local application, tenant, membership, role, idempotency, and audit
   writes together.
4. External identity and metadata failures leave durable, authorized,
   reconcilable state and do not rely solely on best-effort deletion.
5. Duplicate/concurrent public attempts have stable in-progress/replay/conflict
   behavior and cannot create duplicate tenants or identities.
6. Status access is applicant-scoped; tenant endpoints remain inaccessible until
   a valid workspace and tenant authorization exist.
7. Readiness cannot start or extend commercial entitlement; explicit E8 trial
   activation remains the sole new-E8 commercial clock.
8. Legacy cohort classification preserves terms and refuses unsafe automatic
   repair.
9. Architecture tests prove router -> application service -> repository/UoW ->
   infrastructure ownership, without router-owned ORM/session transactions.
10. Isolated PostgreSQL tests prove commit/rollback, concurrency, replay, and
    recovery behavior; frontend acceptance tests prove safe status routing.
