1. Use a read-only query against development to build an exact tenant-ID
   allowlist excluding the protected organization and both protected tenants.
2. Record pre-execution counts per tenant and per dependent table, including
   commercial, membership, staff, clinical, billing, audit, recovery, and
   readiness rows.
3. Confirm every allowlisted tenant is explicitly approved by the owner in the
   future execution request. Do not infer disposability from `TRIAL`, `ACTIVE`,
   or absence of subscription evidence.
4. Obtain a recoverable backup or documented equivalent recovery procedure,
   then validate the protected denylist again immediately before execution.
5. Use application-supported cleanup paths where available. Any necessary SQL
   must be exact-ID scoped, reviewed, and run in dependency order; never use
   `TRUNCATE`, an unrestricted `DELETE`, or broad cascading deletion.
6. Reconcile protected organization/tenant counts and operational accessibility
   after cleanup. Stop on mismatch and restore rather than continuing.

## Dependency and cascade risks

The schema has `RESTRICT` dependencies that must prevent careless deletion:
organization associations, commercial trials, workspace preparation,
provisioning recoveries, ownership verification, signed clinical snapshots,
living-document identities, and treatment-session replacements. It also has
tenant-scoped `CASCADE` dependencies covering users, roles, staff, clients,
appointments, treatments, inventory, prescriptions, invoices/payments,
capabilities, notifications, setup progress, and audit rows.

Consequently, the future execution must inventory child records first and
never issue a parent `org_tenants` deletion until every RESTRICT dependency is
handled through an approved exact-ID plan. Shared organization-level data
(`org_organizations`, memberships, contact/ownership verification, idempotency,
audit, workspace-preparation, and commercial-trial records) requires a separate
ownership check before any action.

## Deterministic reseeding requirements

After cleanup, only isolated synthetic fixtures approved by the lifecycle
services and test factories may be created. The minimum suite is:

| Fixture | Required state | Verification |
| --- | --- | --- |
| Neutral tenant | `NOT_STARTED`, no paid/E8 evidence | Fail-closed operational entitlement |
| E8 trial tenant | Neutral projection plus explicit authorized active E8 trial | Trial entitlement without projection rewrite |
| Paid tenant | One active paid subscription with current period | Paid entitlement wins over trial evidence |
| Expired trial tenant | Non-active/expired E8 trial | No trial entitlement |
| Unauthorized activation | Non-admin or missing confirmation/readiness | Authorization denial and no mutation |
| Incomplete readiness | Readiness not `READY` | Start Trial denied |
| Completed readiness | `READY`, authorized confirmed request | Explicit, idempotent activation only |
| Cross-tenant pair | Separate tenants and actors | No evidence or data leakage |

No fixture may contain real patient data, payment credentials, production-like
personal data, or an invented commercial policy. Fixtures must use the approved
trial and subscription owners; readiness is never inserted as entitlement
evidence.

## Mandatory execution gates

- Separate owner authorization naming the development project and exact
  disposable tenant-ID allowlist.
- Verified protected denylist, dependent-record inventory, and recovery plan.
- Read-only dry-run report of candidate counts before mutation.
- Reviewed execution order and explicit rollback/restore decision point.
- Post-execution protected-count reconciliation and focused commercial,
  tenant-isolation, and authorization tests.

This plan neither executes nor authorizes cleanup.
