# B2.7 ISS-001 — Approval Policy and UX Fitness Inspection

**Date:** 2026-10-16  
**Scope:** Read-only reconciliation of the existing public-registration risk and approval path.  
**Result:** B2.7-B-ISS-001 remains open.

## Executive findings

The original mobile-onboarding requirement approved risk-based approval: low-risk applications may be approved automatically and higher-risk applications go to review. It did not approve the current numeric threshold, component weights, fraud-factor list, or an applicant-owned automatic-approval authority.

The current implementation has an active engine, but does not meet the later owner-ratified D1/PF-018 rule that automatic approval requires authoritative clinic-contact evidence. The public path also records the submitting applicant as reviewed_by for an automatic decision. These are P0 lifecycle/security gaps; no code was changed.

The form has deterministic validation, identity/idempotency protections, applicant-only status reads, and a manual-review screen. Automatic-success and provisioning-recovery messaging are not reliable enough for MVP acceptance.

## AS IMPLEMENTED — actual flow

~~~text
Three-screen clinic-owner form
  -> frontend validation -> registration repository/API client
  -> POST /auth/register-clinic-owner + Idempotency-Key
  -> PublicRegistrationService durable public claim
  -> external identity create/reconcile
  -> SelfRegistrationService creates OrgUser and application
  -> risk score before persistence
  -> DRAFT -> PENDING_REVIEW
  -> risk score again with application ID
  -> APPROVED if eligible; otherwise PENDING_REVIEW
  -> approved path provisions an onboarding workspace
  -> public response -> login -> applicant-only status/root routing
  -> setup/readiness -> separately authorized commercial activation
~~~

The public wrapper protects replay and external identity ownership. Its owner-run PostgreSQL proof covers claim serialization, not risk policy.

## Architecture fitness

Conforming: router -> PublicRegistrationService -> UoW/repositories; frontend presentation -> use case -> repository -> API client; applicant status is authenticated and allowlisted.

Deviation: PublicRegistrationService calls the live legacy SelfRegistrationService with the UoW session. The legacy service and lifecycle service accept raw session/AsyncSession for component validation and provisioning. This is active B2.7 execution, not unused legacy code, and leaves UoW/transaction ownership insufficiently traceable. This report does not prescribe a platform-wide refactor.

## Reconciliation: approved intent versus implementation

| Lens | Evidence-based position |
| --- | --- |
| **AS IMPLEMENTED** | Public registration uses a numeric risk score and hard-coded blocking-factor list to transition a new application from `PENDING_REVIEW` to automatic approval/provisioning. It does not invoke the ADR-PF-018 automatic contact-verification authority. The applicant's own identity is persisted as `reviewed_by` for an automatic approval. The public response includes risk score and factors. |
| **AS APPROVED** | The original onboarding requirement permits low-risk automatic approval and requires high-risk manual review, notification, and audit. The ratified lifecycle contract requires contact ownership and explicitly approved automatic-verification and approval criteria. ADR-PF-018 makes authoritative verified identity the governing source for automatic contact verification and requires provenance/audit with fail-closed handling for unavailable or ambiguous evidence. |
| **GAP** | No owner-ratified score threshold, factor set, weighting, freshness rule, policy version, override authority, or system reviewer/audit identity exists. The required verified-contact evidence is not composed into public registration. The mobile success branch interprets the implemented `onboarding` status as review-pending, and recovery-required users fall through to a generic no-clinic state. |
| **RECOMMENDED CORRECTION** | Keep automatic approval disabled or route cases to manual review until the owner ratifies an approval policy that consumes ADR-PF-018 evidence. Then implement a bounded, versioned policy evaluator, a system decision authority/audit model, non-sensitive public outcomes, and explicit mobile/web approval and recovery status handling. |

## Recommended minimum corrective work

Do not replace the engine or create a generic rules platform. Following narrow owner ratification:

1. Compose PF-018 evidence in the public lifecycle and persist method/version/provenance.
2. Establish server-owned automatic-decision attribution and audit; remove applicant-as-reviewer.
3. Persist one policy-versioned decision snapshot instead of recomputing an outcome in the same command.
4. Replace public risk details with a safe outcome/next-action projection.
5. Repair only automatic-success and safe provisioning-recovery presentation, with contract tests and manual UAT.

Required tests: verified/unverified/mismatched contact; no client assertion; system-not-applicant provenance; policy boundary; replay stability; manual/rejected authorization; provisioning rollback/recovery; commercial neutrality; public response safety; onboarding-success message; recovery route; English/Hindi/screen-reader UAT.

## ISS-001 disposition

**D — existing implementation contains undocumented decisions, and C — the approved verification authority exists but is not integrated.**

ISS-001 cannot close through evidence reconciliation. The next owner decision must ratify exact automatic-approval eligibility criteria consuming PF-018 evidence, the system decision/audit authority, and the policy version. Manual review remains the fail-closed route until that bounded correction is approved and verified.
