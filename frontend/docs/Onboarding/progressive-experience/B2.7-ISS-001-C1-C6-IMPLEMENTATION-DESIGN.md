# B2.7 ISS-001 — C1–C6 Implementation Design

**Date:** 2026-10-16  
**Design status:** `DESIGN_GATE_PARTIALLY_READY`  
**Issue:** `B2.7-B-ISS-001 = OPEN`  
**Parent:** `B2_7_BLOCKED`  
**Scope:** Bounded design only. It preserves the accepted B2.7-B1–B4 lifecycle, public-registration idempotency, applicant-status projection, recovery aggregate, and commercial-neutrality model.

## 1. Ratified direction and design boundaries

The owner recorded `OWNER_RATIFIED_POLICY_DIRECTION_2026_10_16` in the companion [Existing Policy Ratification](./B2.7-ISS-001-EXISTING-POLICY-RATIFICATION.md). That record ratifies six policy **directions**, not numerical calibration, a persistence migration, or implementation acceptance.

The existing automatic-approval engine remains the baseline. This design does not create a replacement engine, rules-management platform, identity provider, OTP system, public-registration workflow, approval state machine, trial/entitlement lifecycle, or clinical workflow.

### Existing to target architecture

```text
CURRENT
Public router -> PublicRegistrationService -> SelfRegistrationService
  -> AutoApprovalService (two evaluations; no PF-018 input)
  -> lifecycle uses applicant as reviewed_by
  -> public DTO includes score/factors/reason

TARGET
Public router -> PublicRegistrationService / public-registration factory
  -> authoritative Identity/verification composition (PF-018-compatible)
  -> one policy-boundary evaluation + immutable decision snapshot
  -> lifecycle/repository/UoW persists system or human decision provenance
  -> B1 provisioning/recovery handoff unchanged
  -> safe applicant outcome projection

Frontend: presentation -> registration/status use case -> repository -> API client
  -> safe outcome/status route -> setup, waiting, verification, progress, or recovery presentation
```

The target has one UoW owner for local registration/decision facts. External provider interaction remains outside a held database transaction, as required by B2.7-B D3/D4. B1 provisioning/recovery remains its separately accepted transaction sequence; approval does not activate a trial or paid entitlement.

## 2. Requirements reconciliation

| Requirement | Design response |
| --- | --- |
| US-2.1 permits risk-based automatic approval and manual review. | Retain engine as an evaluation component, but only a ratified/approved policy basis may permit automatic approval. |
| US-1.2 calls for registration/professional validation. | Separate organization/clinic-owner registration evidence from practitioner credentials. The latter gates clinical privilege activation, not an assumed owner identity. Exact organization evidence still needs formalization. |
| D1 requires contact ownership and explicit criteria. | C1 supplies authoritative contact evidence; C6 supplies one decision snapshot; absent approved basis routes to review. |
| ADR-PF-018 controls verification authority and exact matching. | Reuse its identity port, `supabase_auth_identity_v1`, `clinic_identity_v1`, fail-closed semantics, provenance, audit, and UoW discipline. Do not trust caller flags. |
| B2.7-B2/B3 idempotency and applicant privacy. | Reuse public operation identity/fingerprint and applicant-owned status; no new public scope or recovery state machine. |
| B2.7-B1/B4 recovery and commercial separation. | Approved decision may create a B1 provisioning intent; it never marks readiness, starts a trial, or changes commercial entitlement. |

## 3. C1 — PF-018 verification composition

### Target contract

The public command carries an explicit `primary_contact_kind` (`email` or `mobile`) that names one already submitted clinic contact. Automatic approval requires a PF-018 authoritative exact match for that contact. Any additional submitted contact remains unverified unless separately evidenced under PF-018; it must not be copied, inferred, or described as verified.

| Step | Ownership and behavior |
| --- | --- |
| Identity reconciliation | Existing B2 public-registration operation and authentication authority establish/reconcile the provider user without trusting a caller verification claim. |
| Authoritative read | The existing authoritative identity port resolves only supported provider-confirmed email/mobile for that provider user, using `supabase_auth_identity_v1`. |
| Normalization/match | Existing `clinic_identity_v1` normalizers compare the designated submitted contact against the same-kind authoritative contact. |
| Evidence | A successful decision retains only an opaque evidence reference/method/version; unavailable, unconfirmed, mismatched, malformed, or ambiguous evidence returns a safe `verification_required`/manual-review outcome. |
| Idempotency | The existing B2 public operation controls replay. Exact replay returns the original safe outcome and must not reissue or consume evidence differently. |
| Transaction | Identity/provider reads are outside a held mutation transaction. Local application decision/provenance, audit/outbox, and public-operation completion commit together through the existing UoW. |

### Current architecture incompatibility requiring a design-resolution spike

`AutomaticContactVerificationStrategy` and `ClinicContactVerificationService` are currently organization-scoped: they require `organization_id`, authenticated `actor_id`, an organization permission, and an allowed `clinic_entry.*` intended operation. Public registration is intentionally pre-organization and begins unauthenticated; its accepted B2 scope uses a server-owned subject/correlation identity instead. The existing `SupabaseIdentityProvider` takes a `CurrentUser` with server-validated raw claims, while the public registration flow presently receives provider identity data through `AuthProvider` and does not supply that PF-018 principal/evidence contract.

This is not permission to create a parallel identity mechanism or evidence table. Before C1 implementation, an ADR-PF-018-compatible adaptation must be designed that reuses the existing identity provider/evidence lifecycle while binding evidence to the B2 public subject/operation rather than a fabricated organization. It may require an additive extension to the existing evidence service/operation allow-list and a reviewed pre-organization authorization scope. The outcome cannot be silently assumed from the organization-scoped API.

**C1 status:** `DESIGN_PENDING_TECHNICAL_COMPATIBILITY`. This is a genuine architecture/design gate, not a new product decision.

## 4. C2 — typed system decision and audit attribution

### Required model

Automatic approval must never populate `org_tenant_applications.reviewed_by` with the applicant. Human manual review retains `reviewed_by`, `reviewed_at`, review notes, and override attribution.

The smallest proposed additive application-decision fields are:

| Proposed field | Meaning |
| --- | --- |
| `automatic_decision_actor_type` | Fixed typed classification for the approved application-decision system authority. |
| `automatic_decision_method_version` | Evaluator/identity method version. |
| `automatic_decision_policy_version` | Immutable approved risk-policy identifier/version. |
| `automatic_decision_at` | UTC decision timestamp. |
| `automatic_decision_reason_code` | Safe controlled code, not factor detail. |
| `automatic_decision_evidence_ref` | Opaque PF-018-compatible evidence reference; never a contact/token. |

The existing `reviewed_by` remains nullable and is null for a system decision. A Platform Audit/outbox event records actor classification, decision metadata, safe correlation reference, outcome, and no raw contacts/factors/exceptions. A human manual approval/rejection emits the existing human actor audit facts.

### Persistence and migration assessment

Existing application columns cannot safely enforce the owner direction: `reviewed_by` is a human `org_users` foreign key and `application_data.system` is untyped JSONB. Storing the new provenance only in JSONB would not enforce null-human/system consistency or provide a durable typed audit shape. The design therefore expects one additive migration on `org_tenant_applications`, with nullable new fields for compatibility and constraints that require a complete automatic set when `automatic_decision_actor_type` is present and prohibit an automatic decision from retaining `reviewed_by`.

No backfill is needed for legacy/disposable MVP rows: legacy rows retain their historical meaning and no automatic provenance is fabricated. Ayurvaidik Parishkar Kendra and all other records remain untouched. Deployment is additive: migration -> compatible writer/reader -> verification -> later enforcement only if separately approved. Rollback is application rollback first; schema rollback occurs only under the normal migration protocol and never rewrites stored history.

**C2 status:** `DESIGN_READY_SUBJECT_TO_C1_EVIDENCE_SHAPE`.

## 5. C3 — privacy-safe public DTO projection

### Public contract

The public registration response must remove `risk_score`, `risk_factors`, and internal reason text. Internal application/audit/admin projections remain separate and authorized.

| Retain / add as safe | Remove from public registration DTO |
| --- | --- |
| `success`, stable `application_id` where already accepted, safe `application_status`/outcome, `next_action`, safe display message key, optional setup eligibility/recovery status | Risk score, factor strings, fraud reason, evaluator recommendation, verification evidence/reference, internal recovery operation ID, raw provider/database errors. |

Public error responses use stable safe codes/messages only. The frontend maps the safe outcome to localized content; it never owns risk/approval policy. Admin-only DTOs retain only the internal information that their existing authorization contract allows.

**C3 status:** `DESIGN_READY`, dependent on C1/C2 outcome vocabulary.

## 6. C4 — approved applicant continuation

When the existing backend returns `application_status="onboarding"` after successful workspace provisioning, the frontend must treat it as approved setup continuation—not as pending review. It keeps the current registration-session finalization and authenticated root gate, then directs the owner to the existing setup wizard only when the tenant/status projection permits it.

| Outcome | Existing correction target |
| --- | --- |
| Approved and workspace provisioned (`onboarding`) | Localized approved/setup continuation, then authenticated setup route; no pending-review alert. |
| Pending review | Existing waiting/status screen with refresh/sign-out; no score disclosure. |
| Verification required | Safe localized guidance and resume/refresh action; no provider diagnostics. |
| Rejected | Existing authorized rejection route/message; no automatic rejection behavior added. |

Navigation must not bypass B1 readiness, B4 commercial entitlement, or tenant authorization guards.

**C4 status:** `DESIGN_READY`, dependent on C3 safe outcome projection.

## 7. C5 — applicant recovery experience

Reuse the accepted B3 applicant-owned status projection. Do not expose recovery operation IDs or create another recovery aggregate.

| Status projection | Presentation behavior |
| --- | --- |
| `provisioning_pending` / `provisioning_in_progress` | Authenticated preparation screen: truthful progress, refresh, sign out, and no false workspace success. |
| `provisioning_recovery_required` | Authenticated safe recovery screen: clear continuation/support action, refresh, no tenant ID, operation ID, or raw failure detail. |
| `provisioning_completed` | Root refreshes authoritative session/status and continues only through existing tenant/setup guards. |
| interrupted session | Re-authenticate, fetch applicant-owned status, and render only the safe corresponding state. |

The actual retry authority remains backend-owned under B1 recovery semantics. If the approved recovery API already supports applicant-authorized retry, the screen invokes only that existing safe command; otherwise it offers refresh/support, not a client-created retry mutation.

**C5 status:** `DESIGN_READY`, dependent on C3 outcome mapping and confirmation of existing retry transport.

## 8. C6 — policy boundary and immutable decision snapshot

### Proposed minimal representation

At one authoritative final point after C1 evidence and C2 provenance inputs are available, the existing evaluator returns a frozen domain result:

```text
policy_id/version
eligible / manual_review
ordered factor codes (internal only)
safe reason code
verified-contact evidence reference
decision time
```

The policy boundary—not a new engine—filters the existing engine inputs into:

1. identity eligibility gate;
2. approved organization/business validation gate;
3. owner-ratified defensible indicators;
4. hard-blocker/manual-review routing;
5. automatic-approval eligibility.

Factor codes are deterministically ordered (for example an explicit canonical policy order) before snapshot/audit persistence; `list(set(...))` must not control stored evidence order. An accepted decision is replayed from the B2 operation/result and snapshot, not rescored. A manual-review outcome may be re-evaluated only through a separately authorized human-review/override operation; it is not silently changed by retry.

### Double-evaluation resolution

Remove the pre-persistence decision as a lifecycle authority. It may at most remain an internal non-authoritative recommendation if separately justified; it must not be persisted as the accepted decision or returned publicly. After the public operation and required evidence are available, evaluate once, persist one snapshot, transition to approved or review, and commit with audit/outbox facts. Historical lookup behavior must be either implemented through its approved repository contract and included in policy evidence, or excluded from the ratified policy; current placeholder helpers cannot be represented as active historical protection.

**C6 status:** `DESIGN_PENDING_NUMERIC_POLICY`: implementation cannot safely select retained factor codes or a numeric threshold until D-ISS001-1's evidence-backed factor/calibration decision is complete.

## 9. Human override design

The existing admin review route uses `require_org_admin_dict` and passes its `org_user_id` to lifecycle approval/rejection. Its current authorization is organization-admin rather than a demonstrated, dedicated application-review permission.

Target behavior:

- reuse an existing application-review permission if source inspection proves it governs this route; otherwise a new permission is a separate owner/security approval, not an implementation convenience;
- allow explicit human approve/reject only from `pending_review` under normal lifecycle/OCC locking;
- require non-empty controlled reason/justification and actor/timestamp/audit fact;
- never allow a normal human override to mark a PF-018 verification failure automatically satisfied;
- manual proof of contact, if product later allows it, must use the existing PF-018 manual evidence lifecycle and an explicitly approved authority;
- preserve idempotent replay and return conflict for stale/competing review decisions.

**Unresolved dependency:** exact existing permission coverage and service signature consistency require a focused implementation-time authorization audit. No new privileged role is designed here.

## 10. Frontend data and navigation design

```text
Registration screen
 -> existing register use case/repository/API client
 -> safe registration outcome projection
 -> finalize registration session
 -> login/authenticated root gate
 -> applicant-owned status projection
 -> setup | pending review | verification guidance | progress | recovery | rejected
```

The registration form must make the primary clinic contact designation explicit only if it is not already semantically identical to the existing sole `primary_contact`. It must not ask the applicant to re-enter identity information or expose confirmation timestamps. English/Hindi keys belong in the existing localization system; presentation tests assert message keys/outcomes rather than risk data.

## 11. Focused verification matrix

| Area | Required evidence |
| --- | --- |
| C1 identity | exact designated email/mobile match; unconfirmed/mismatch/ambiguous/unavailable fail closed; additional-contact semantics; no caller flag/profile trust; replay does not reconsume evidence. |
| C2 provenance | system decision has no human reviewer; complete typed provenance/audit/outbox; human review retains actor; rollback leaves no partial decision fact. |
| C3 privacy | registration DTO/error/debug projection contains no score/factor/reason/evidence/internal operation ID; authorized internal projection stays authorized. |
| C4 UX | `onboarding` shows approved continuation; pending/rejected remain correct; no readiness/commercial bypass; web/mobile finalization. |
| C5 recovery | progress/recovery status route; interrupted session; safe refresh/support; applicant isolation; no tenant/recovery identifier leakage. |
| C6 policy | ordered factors; one snapshot; replay stability; no rescore after decision; ratified threshold/blocker boundaries; historical source behavior. |
| Existing B2.7 protections | duplicate registration, idempotent operation, identity reconciliation, recovery, commercial neutrality, and applicant isolation regressions. |
| Manual UAT | first-time web/mobile registration; returning applicant; interrupted flow; English/Hindi; keyboard and screen reader; non-technical clinic-owner comprehension. |

Use isolated PostgreSQL only if the approved C1/C2/C6 persistence schema or transaction behavior is changed. Do not rerun B1–B4 broad acceptance merely for design.

## 12. Implementation sequence and rollback

1. Resolve C1 technical compatibility and D-ISS001-1 numeric/factor policy gate.
2. Design/review the single additive migration for C2/C6, if still needed, and run focused migration compatibility review.
3. Implement C1+C2+C6 as one backend transactional decision slice, preserving B2 operation replay and B1 recovery handoff.
4. Implement C3 public projection in the same API compatibility slice.
5. Implement C4+C5 frontend outcome/status presentation with localization and routing tests.
6. Run focused deterministic, privacy, authorization, transaction, and any necessary isolated PostgreSQL tests; then conduct manual UAT.

Rollback: stop automatic approval by routing no fully authorized basis to the existing manual-review path; retain already committed valid decisions and recovery records; never recreate tenants or identities. Application rollback must remain schema-compatible with additive nullable columns. Migration rollback is separately reviewed and may never fabricate/rewrite legacy decision facts.

## 14. Acceptance criteria

The C1–C6 program is accepted only when:

- automatic approval has a ratified factor/version/threshold basis and PF-018-compatible evidence binding;
- every automatic decision persists typed system provenance with null human reviewer;
- replay returns an immutable prior outcome rather than rescoring;
- public outputs and frontend state expose only safe outcomes/actions;
- approved `onboarding` routes toward setup, and recovery/progress routes are truthful and safe;
- B1–B4 idempotency, recovery, applicant isolation, and commercial neutrality regressions remain passing;
- any approved additive migration is compatible, reversible under its reviewed plan, and does not mutate protected/legacy records;
- focused automated and manual accessibility/localization evidence passes.

## 15. Safety and governance

Documentation-only design. No production/backend/frontend implementation, executable tests, migrations, database/Supabase operation, test-data change, staging, commit, push, merge, reset, rebase, or branch change is authorized or performed. B2.7 remains blocked; FO-002, FO-001, protected legacy findings, and B2.8 remain untouched.
