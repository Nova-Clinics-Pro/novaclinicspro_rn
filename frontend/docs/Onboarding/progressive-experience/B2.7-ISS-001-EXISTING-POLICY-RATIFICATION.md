## 1. Executive finding

The existing engine already implements a risk-based automatic-approval path. It
is retained here as historical implementation evidence only. MVP-ONB-002 now
selects manual review only for the initial MVP; this record does **not**
recommend a replacement scoring engine, a new rules platform, or an automatic
approval implementation for that phase.

However, automatic approval cannot presently satisfy the approved B2.7-B D1/PF-018 contract: its exact threshold, component weights, hard blockers, identity prerequisite, policy version, and automated-decision authority are not owner-ratified. It also does not consume authoritative contact-verification evidence, stores the applicant as the reviewer of an automatic approval, and returns internal decision details to an anonymous applicant.

The smallest viable direction is: ratify the existing decision policy (with listed corrective constraints), compose existing PF-018 evidence into the existing public command, persist an auditable non-human approval decision without a fabricated user, return a safe outcome projection, and correct the existing status presentation/recovery routes.

## 3. Exact implemented risk and approval policy

### 3.1 Decision algorithm

```text
advanced_score = clamp(base * 0.40 + historical * 0.25 + geographic * 0.15 + fraud * 0.20, 0, 1)
advanced_score is rounded to 3 decimal places before combination
legacy_score = clamp(base + profile + contact + context, 0, 1)
combined_score = advanced_score * 0.80 + legacy_score * 0.20

AUTO_APPROVE iff:
  combined_score < 0.95
  AND no factor contains any exact blocker substring:
      temporary_email_domain
      test_business_name
      test_contact_name
      high_failure_rate_domain
      multiple_recent_applications
      suspicious_phone_pattern
      platform_source_mismatch
Otherwise: PENDING_REVIEW.
```

`AUTO_APPROVAL_THRESHOLD` and `HIGH_RISK_THRESHOLD` are both exactly `0.95`. The active enhanced decision uses `< 0.95`; the older comparison helper uses `<= 0.95`, but does not control the active lifecycle decision. No automatic rejection branch exists: a non-eligible complete application remains `pending_review`. An evaluation/DTO-conversion exception is treated as ineligible with score `1.0` and factor `auto_approval_evaluation_failed`.

The combined factor list is formed through `list(set(...))`; membership controls eligibility, but factor ordering in the returned response/audit payload is not deterministic.

## 5. PF-018 integration contract

### As approved

- The identity owner is `IAuthoritativeUserIdentityProvider`, using Version 1 method key `supabase_auth_identity_v1`.
- Confirmed email and confirmed mobile are independently authoritative only when the provider supplies supported confirmation state/timestamp.
- Submitted clinic contacts normalize through `clinic_identity_v1` and must exactly match corresponding confirmed identity values.
- Unavailable, ambiguous, unconfirmed, invalid, or unsupported confirmation semantics fail closed; the applicable result is manual review, not automatic approval.
- Public registration must never trust a caller-supplied verified flag, user metadata, `/auth/me`, profile, organization, or tenant contact as evidence.

### Minimum composition required

`POST /auth/register-clinic-owner` must compose the existing identity/evidence service at the public command decision point, place only opaque verification evidence/provenance in the existing lifecycle/UoW flow, and pass a verified/not-verified decision input into the existing approval evaluator. It must not create a new identity provider, evidence store, verification table, or parallel verification workflow.

**Owner decision required:** because the current public form submits both email and mobile, ratify whether automatic approval requires both values to be confirmed/exact matched, or whether the user must explicitly designate one submitted clinic contact. PF-018 governs exact matching once a contact is submitted; it does not silently choose which contact is mandatory for this registration policy.

## 9. Focused acceptance specification

### Backend deterministic/regression coverage

1. Each ratified advanced and legacy factor value; component weights; exact `< 0.95` boundary; every hard blocker; non-blocking factor behavior.
2. Deterministic factor ordering and a single persisted decision snapshot; replay cannot change an accepted decision.
3. Confirmed exact-email/mobile match according to the ratified contact rule; unconfirmed, mismatched, unavailable, ambiguous, expired (if the identity provider returns expiry), and client-asserted evidence all route to review.
4. No automatic approval before required registration/professional validation has succeeded, or an owner-approved narrowing explicitly governs the requirement.
5. Automated attribution is system provenance with no applicant/human reviewer; human manual approval/rejection and authorized override retain proper reviewer identity.
6. Applicant-only status isolation, duplicate public registration, idempotent operation replay, and external-identity reconciliation remain covered.
7. Public response carries only safe outcome fields; authorized internal review preserves necessary internal evidence.
8. Approval/provisioning failure retains valid approval and uses existing recovery semantics; commercial neutrality remains unchanged.

### Frontend contract and UAT coverage

1. Auto-approved `onboarding` registration response gives setup/login continuation, never review-pending copy.
2. Pending-review, verification-required, in-progress, recovery-required, already-registered, and rejected safe outcomes each select the correct route/message.
3. Root/session restoration uses authenticated applicant status and never exposes cross-applicant/tenant data.
4. English/Hindi rendering, keyboard focus, labels, screen-reader order, refresh/retry/support affordances, and interrupted-network recovery receive manual acceptance evidence.

No database, migration, or B1–B4 accepted suite is required merely to document this specification. Isolated PostgreSQL verification is required only if the approved C2/C6 persistence design adds decision/provenance fields or changes transactional lifecycle behavior.

## 12. ISS-001 closure conditions

- D-ISS001-1 through D-ISS001-6 are ratified or their governing requirements are formally amended.
- The public automatic-approval path consumes PF-018-authoritative evidence and fails closed to review when it is absent or unusable.
- An automatic decision has truthful, typed system provenance; no applicant is represented as reviewer.
- The public response and frontend never expose internal score/factor/reason data.
- Approved, pending, verification, provisioning, and recovery journeys provide safe, correct next actions.
- Required focused tests, any necessary isolated PostgreSQL transactional evidence, and English/Hindi/accessibility UAT pass.
- `B2.7-B-ISS-001` remains explicitly preserved until those conditions are verified; `B2.7-FO-002`, `B2.7-FO-001`, `LEGACY-ONB-001/002`, and `B2.8-ISS-001` are not redefined or closed by this work.
