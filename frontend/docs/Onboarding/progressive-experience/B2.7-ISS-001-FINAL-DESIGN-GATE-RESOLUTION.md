# B2.7 ISS-001 Final Design-Gate Resolution

**Status:** `DESIGN_PARTIALLY_BLOCKED`
**Scope:** design contract only; C1–C6 are not implemented.
**Governance:** `B2.7-B-ISS-001 = OPEN`; `B2_7_BLOCKED` remains in force.

## 1. Evidence and boundary

This resolution is based on the transferred ISS-001 baseline, the B2.7-B
lifecycle contract, ADR-PF-018, the mobile-onboarding US-1.2 and US-2.1
requirements, and source inspection in the isolated backend/frontend worktrees.
It does not assert live database or provider behaviour.

| Evidence class | Verified finding |
| --- | --- |
| Source-verified | Public registration has a durable B2 operation/replay path and provider identity reconciliation, but its request has no explicit primary-contact designation. |
| Source-verified | `ClinicContactVerificationService` is organization/actor scoped and its allowed operations are clinic-entry operations; it cannot be reused unchanged by a pre-organization public registration. |
| Source-verified | ADR-PF-018 requires server-authoritative Supabase identity evidence, exact normalized contact matching, fail-closed behaviour, existing evidence lifecycle/UoW reuse, and no fabricated human authority. |
| Source-verified | The current `< 0.95` numeric threshold cannot discriminate as intended: the source-derived maximum combined score is about `0.5904`. |
| Source-verified | Current application review is reached through `require_org_admin_dict`; no separately demonstrated platform-review permission or verified pre-organization ownership scope was found. |
| Reasoned design | The smallest safe route is one public-operation-scoped extension of the existing authoritative-identity and clinic-contact-evidence lifecycle, not a second identity provider, OTP flow, evidence store, or registration engine. |

No recommendation below is owner-approved merely because it is documented here.

## 3. G1 — PF-018 public-operation identity binding

### Existing contracts

- ADR-PF-018 makes `IAuthoritativeUserIdentityProvider` the authority for
  confirmed email/mobile evidence and fixes `supabase_auth_identity_v1` as the
  Version 1 method key.
- B2 public registration already owns the durable operation, replay key,
  request fingerprint, and external provider-user reconciliation.
- Existing clinic-contact verification owns normalization, opaque evidence,
  lifecycle application, audit, idempotency, and a UoW; it is presently
  organization/actor scoped.

### Proposed minimal additions

1. Add immutable application input `PublicRegistrationIdentityContext`:
   `public_operation_id`, `public_subject_ref`, and reconciled
   `provider_user_id`. It is constructed only by the public-registration
   composition root after it has loaded the durable B2 operation; it is never
   accepted from an HTTP client.
2. Add one server-only method to the existing authoritative identity port,
   conceptually `get_identity_for_public_registration(context)`. The Supabase
   adapter must confirm that the provider user ID equals the operation's
   persisted external identity before returning confirmed email/mobile and the
   immutable provider method/version. It must not accept arbitrary provider
   user IDs, client claims, profiles, `/auth/me`, or metadata as evidence.
3. Add a public-registration operation scope to the existing clinic-contact
   verification lifecycle, for operation
   `public.register_clinic_owner.v1`. It uses the same normalizer, provider,
   opaque evidence reference, audit, and UoW. Its scope is the B2 operation and
   keyed public-subject reference, not a fabricated organization or actor.
4. If the current evidence schema cannot represent that exclusive public scope,
   extend that *existing* evidence record with nullable pre-organization scope
   columns and a constraint requiring exactly one scope: organization/actor or
   public-operation/subject. Do not introduce a new evidence table or store.
5. Exact replay reads the stored decision/evidence correlation and does not
   call, consume, or issue evidence again. A missing, unconfirmed, ambiguous,
   mismatched, or unavailable authoritative attribute produces a safe
   `pending_review` outcome; it never produces automatic approval.

The public-registration server composition is the only authority allowed to
request this scope. Strategies cannot create a tenant, association, grant, or
commit independently.

## 4. G2 — recommended MVP risk policy

No defensible calibrated numeric threshold exists in the current evidence. The
owner has ratified a hybrid direction: retain the engine, use a versioned
**blocker-led deterministic MVP policy**, and defer numerical approval authority
until separate calibration approval. `public_registration_risk_v1` is a
proposed identifier, not factor approval. Automatic approval remains possible
only when all G1/G3 evidence gates pass, the subsequently ratified deterministic
rules do not require review, and the final policy snapshot is persisted.
Otherwise, route to manual review.

| Factor family | Recommendation | Reason |
| --- | --- | --- |
| Authoritative designated-contact exact match | Required eligibility gate | ADR-PF-018 requirement; not a score. |
| Temporary email domain | Manual-review context only | Plausible abuse signal, but current substring matching can false-positive. |
| Suspicious contact patterns | Manual-review context only | Deterministic triage signal, not authoritative identity proof. |
| Test business/contact names | Manual-review context only | Protects test/abuse routing but substring matching can false-positive. |
| Platform/source mismatch | Manual-review context only | Current value is caller-supplied; it cannot alone establish fraud. |
| Historical repeats/failure rate | Requires further evidence | Current helpers return empty lists; no live signal-of-interest was proven. |
| Geographic factors | Exclude from automatic approval | Unsupported and fairness-sensitive. |
| Specialty, clinic type, staff size, operating hours, requested components | Exclude from automatic approval | Operational/product context, not validated abuse evidence. |
| Budget, urgency, referral, guided-tour data | Exclude from automatic approval | Commercial/onboarding preference, not identity or fraud evidence. |
| Optional registration/tax information | Not an automatic-risk signal | May be used only after G3 approves evidence authority; GST/PAN are not silently mandatory. |

**Required ratification:** exact retained codes, their manual-review effect,
the immutable policy version, and whether an all-clear blocker-led outcome is
sufficient for automatic approval. Do not lower `0.95`, invent weights, or
claim calibration without governed evidence.

## 5. G3 — organization evidence and US-1.2

Clinic-owner identity, organization/clinic registration, practitioner
credentials, and clinical privileges are separate responsibilities. A clinic
owner is not presumed to be a clinician. Practitioner credential validation
belongs when a practitioner is assigned the corresponding clinical role or
privilege.

### Proposed US-1.2 supplement — not yet approved

> During public organization/clinic-owner registration, collect the business
> context needed for component recommendation. Automatic approval requires
> organization/clinic registration evidence from an owner-approved applicable
> authority. If required evidence is absent, unavailable, ambiguous, or cannot
> be validated, route the application to manual review. Practitioner credential
> validation is performed later when a practitioner is assigned a clinical
> role/privilege. GST/PAN or any tax identifier is optional unless a governing
> jurisdictional policy explicitly requires it.

Recommended MVP evidence contract for owner approval: registered
organization/clinic name, jurisdiction, registration authority/type and
identifier where applicable, evidence-reference metadata, and applicant
attestation. It must use an approved authoritative validation capability before
it can enable automatic approval. Absent that capability, the safe result is
manual review—not an implicit waiver.

## 6. G4 — human review authority

Current verified route flow is:

`admin_applications_router` → `require_org_admin_dict` →
`AdminApplicationsService.review_application` → lifecycle approve/reject.

The lifecycle writes a human `reviewed_by` identity for human review and emits
the existing audit/event facts. Current evidence does not prove that global
organization-admin membership is an approved platform-level authority to review
applications that exist before an organization/tenant relationship, nor does it
prove an existing dedicated application-review permission.

### Required owner choice

1. Ratify the existing platform-operated org-admin audience as the review
   authority for these pre-organization applications, with the existing
   approve/reject transitions; **or**
2. identify an already-granted dedicated permission and its composition path;
   **or**
3. authorize a separate permission/scope as later work.

Recommendation: choose option 1 only if Platform Security confirms the
existing org-admin population is intentionally the platform review audience.
Reviewer reason, actor, timestamp, and audit must be enforced for an override.
A failed G1 automatic check may enter review, but a reviewer cannot represent
the contact as authoritatively verified unless the approved manual PF-018
lifecycle produces that evidence.

## 7. G5 — contact designation semantics

The current request captures clinic `primary_contact.email` and
`primary_contact.phone`; it has no designation field. Add
`primary_contact_kind: email | mobile` naming one already submitted value.

- The designated field is normalized and compared with the same-kind confirmed
  authoritative attribute under `clinic_identity_v1`.
- The other submitted value is ordinary contact data only. It is not copied,
  inferred, displayed as verified, or promoted into evidence.
- Existing request compatibility can retain both fields initially; the UI adds
  only a selection over values the applicant already supplied. It must not ask
  for a duplicate contact entry.
- A later contract amendment may permit omission of the non-designated field,
  but that is not included in C1–C6 until API compatibility is approved.
- At least one email/mobile remains the onboarding minimum through the
  designated field. No contact confirmation timestamp or provider detail is
  exposed to the applicant.

## 8. G6 — typed automatic-decision provenance

An additive migration is necessary: `reviewed_by` is a human `org_users` foreign
key and existing `application_data.system` JSON is not a typed, enforceable
system decision record.

### Proposed nullable compatibility fields on `org_tenant_applications`

| Field | Purpose |
| --- | --- |
| `automatic_decision_actor_type` | Fixed value `public_registration_system`. |
| `automatic_decision_method_version` | Identity/evaluator method version(s). |
| `automatic_decision_policy_version` | Ratified immutable policy identifier/version. |
| `automatic_decision_at` | UTC final decision time. |
| `automatic_decision_reason_code` | Controlled safe outcome code. |
| `automatic_decision_evidence_ref` | Opaque evidence reference, never PII/token. |
| `automatic_decision_factor_codes` | Ordered internal factor-code snapshot; no raw contact, claims, or secrets. |

The migration must add a paired-field constraint: either every automatic field
is null (legacy/human decision) or the automatic actor is the fixed system
authority, all required automatic fields are non-null, and `reviewed_by` is
null. It must not backfill or fabricate history.

Application lifecycle/repository rules enforce one final automatic transition:
only the pending-review transition writes the immutable snapshot; later updates
cannot replace it. The same UoW persists application status, provenance,
existing audit/outbox facts, and B2 operation completion. External identity
calls happen outside the held local transaction. Exact replay returns the stored
decision rather than rescoring or rewriting provenance.

## 9. Minimal implementation sequence

1. **C1:** public-operation identity/evidence scope and primary-contact
   designation, after the G1 scope decision.
2. **C2 + C6:** one additive migration; lifecycle/repository/UoW decision
   persistence and frozen policy snapshot, after G2/G3 approval.
3. **C3:** public-safe projection only—stable application identifier, safe
   status/outcome, next action and message key; omit score, factors, internal
   reason, evidence reference, recovery ID, and raw failures.
4. **C4 + C5:** frontend continuation/recovery routing. Approved means setup
   continuation, never readiness or commercial entitlement bypass; pending or
   recovery views expose no operational identifier.
5. **Verification/UAT:** focused deterministic suites first, then owner-run
   isolated PostgreSQL mutation/concurrency tests and accessibility/manual UAT.

## 12. Readiness disposition

The technical design is sufficiently specific to estimate and implement without
creating parallel providers, stores, or transactions. It is **not** authorized
for implementation until OD-1 through OD-6 are resolved. The only safe current
automatic path is fail-closed to manual review where any required authoritative
evidence or policy approval is unavailable.

commit, push, or merge was changed by this design-resolution task.
