## 1. Ratified Option A and acceptance criteria

**Historical Option A statement (superseded for the initial MVP):** automatic
clinic-registration approval was mandatory for the 30-day registration/onboarding
MVP launch. MVP-ONB-002 replaces that launch policy with manual review only.
The hybrid strategy remains long-term architecture:

- authoritative designated-primary-contact verification;
- authoritative applicable organization-registration validation;
- owner-approved deterministic review rules;
- existing score engine retained but never authorized by the uncalibrated
  `0.95` threshold; and
- manual review, not automatic rejection, when evidence or deterministic
  eligibility is inconclusive.

MVP automatic approval is accepted only when all of these hold: the server
binds the public operation to the reconciled provider subject; PF-018 confirms
the selected contact with an exact normalized match; an approved authority
validates applicable organization evidence; a versioned deterministic policy
has no review trigger; the system provenance snapshot is atomically durable;
and the safe public result gives approved continuation without leaking internal
risk/evidence details.

The 30-day target is a planning constraint, not a verified schedule or a reason
to waive an authority, security, or acceptance gate. No start date or remaining
duration is documented.

## 2. Organization-validator critical path

### Source finding

The accepted requirements require registration/professional validation but do
not name an MVP geography, legal entity category, clinic category, registry, or
authoritative validation capability. The source has India-oriented legacy
signals, but those are not an approved jurisdiction scope. No existing
organization-validator port, adapter, or authoritative integration was found.

Therefore the current result is:

`AUTO_APPROVAL_AUTHORITY_UNVERIFIED`

A clean score, self-attestation, uploaded document, unofficial lookup, screen
scrape, tax identifier, or practitioner licence alone is not authoritative
organization validation. No single registry should be assumed to prove
organization existence, legal operating status, registration-number validity,
applicant representative authority, clinic licensure, practitioner credential,
and contact ownership.

### Authority options

| Option | What it can prove | MVP feasibility now | Limitation / manual-review result |
| --- | --- | --- | --- |
| Official registry/API chosen for an approved jurisdiction and entity type | Only its documented registration/status fields | Candidate after Product/Security select jurisdiction, registry, access terms, and matching policy | Provider timeout, no match, ambiguity, unsupported entity, or no entitlement → manual review |
| Official supported verification interface without API | Only the documented registry result, subject to permitted automation terms | Requires explicit legal/security approval before integration | No scraping; unavailable interface → manual review |
| Authorized third-party verifier with documented source provenance | Contract-defined registry checks only | Requires procurement, data-processing, reliability, and licensing review | Not authoritative unless source/provenance and contractual authority are approved |
| Self-attestation or uploaded evidence | Applicant claim/document only | Manual-review evidence only | Cannot enable automatic approval |
| Unofficial lookup/screen scrape | None suitable for this policy | Not permitted | Never enables automatic approval |

No option is presently selected or usable. The smallest legitimate resolution is
an owner-selected **initial jurisdiction + entity/clinic category + official
authority**, followed by Platform Security review of source provenance, access
terms, PII/data-minimization, matching rules, availability, expiry, and fallback
to manual review. This is the launch-critical dependency.

## 3. Proposed narrow validator architecture

This is a proposed interface, not implemented architecture.

`IOrganizationEvidenceValidator.validate(request)` is a single domain/app
port, composed by the public-registration factory with the existing UoW and
existing audit/outbox boundaries. The request contains only normalized legal
organization identity, approved jurisdiction/entity type, registration
identifier where applicable, B2 public-operation correlation, and policy
version. It must never receive unrelated applicant profiles or raw provider
claims.

The result contains: `verified | not_verified | unavailable | unsupported |
ambiguous`, authority/source key, opaque authority evidence reference, verified
identity match summary, checked-at time, optional expiry, safe reason code, and
validator method/version. It does not return raw registry payloads to public
DTOs. A provider timeout/unavailability is `unavailable` and routes to manual
review. The B2 operation stores/correlates a replay-stable result; exact replay
does not repeat an external lookup unless an explicit expiry/recheck policy
later authorizes it.

The adapter owns external calls and credentials; the application service owns
policy composition; the existing UoW owns only local state/audit/outbox
persistence. No external request runs while a local row lock is held, no adapter
commits independently, and no generic verification framework or second
onboarding engine is introduced. Deterministic tests use a mockable adapter
returning each status; isolated PostgreSQL proof is required only after
persistence changes are authorized.
