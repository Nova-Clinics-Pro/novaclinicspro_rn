# B2.7 ISS-001 — Risk Policy Fitness, Fairness, and Owner Decisions

**Date:** 2026-10-16  
**Status:** `B2.7-B-ISS-001 = PRODUCT_DECISION_REQUIRED`  
**Scope:** Read-only source reconciliation and database-free deterministic evaluation of the existing public-registration approval engine.  
**Not an approval:** Recommendations below are not owner ratification and authorize no implementation.

## 1. Executive assessment

The existing engine distinguishes obvious synthetic fraud/abuse signals from ordinary registration profiles principally through seven hard blockers. That is meaningful as a narrow abuse-routing mechanism. Its numeric threshold does **not** currently provide meaningful risk discrimination: the source-derived maximum reachable combined score in the current implementation is approximately `0.5904`, below the `< 0.95` manual-review boundary. A deliberately adverse executed profile reached `0.5896` and was routed to review only because it triggered hard blockers.

Consequently, the current system is effectively:

```text
AUTO_APPROVE unless a hard blocker is emitted
```

not a calibrated score-threshold decision. This does not mean automatic approval should be removed or replaced with manual review. It means the owner must either ratify the engine honestly as a blocker-led MVP policy with a non-operative threshold, or commission bounded calibration evidence before relying on its numeric threshold as a security control.

The current engine also conflicts with D1/PF-018 because it has no authoritative contact-verification input, attributes an automated approval to the applicant, and exposes detailed internal decision evidence publicly. Geographic, clinic-type, and operational scores currently cause simulated score differences but do not change approval outcomes because the threshold is unreachable; they nevertheless lack approved fraud justification and are unsafe to preserve as future calibrated decision inputs without evidence.

## 4. Exact current scoring implementation

```text
advanced = round(clamp(base*0.40 + history*0.25 + geography*0.15 + fraud*0.20, 0, 1), 3)
legacy = clamp(clinic/components + profile + operations/contact + app context, 0, 1)
combined = advanced*0.80 + legacy*0.20

approve iff combined < 0.95 and no hard blocker factor is present
otherwise leave the completed application PENDING_REVIEW
```

The active threshold is `0.95`, using a strict `<` comparison. The legacy comparison helper has `<= 0.95`, but the lifecycle uses the enhanced decision. The active hard blockers are:

1. `temporary_email_domain`
2. `test_business_name`
3. `test_contact_name`
4. `high_failure_rate_domain`
5. `multiple_recent_applications`
6. `suspicious_phone_pattern`
7. `platform_source_mismatch`

The existing policy inventory, exact individual values, and source locations are retained in [Existing Policy Ratification](./B2.7-ISS-001-EXISTING-POLICY-RATIFICATION.md). Material properties verified in this assessment:

- advanced components weigh base `0.40`, history `0.25`, geography `0.15`, fraud `0.20`;
- the advanced/legacy blend weighs `0.80`/`0.20`;
- `list(set(...))` deduplicates factors but makes returned factor ordering nondeterministic;
- history lookup helpers currently return empty lists in the implementation, so historical factors cannot arise in the current unmodified source path;
- a pre-persistence and a post-persistence evaluation occur, but current placeholder history methods make application ID inert for the evaluated ordinary scenario;
- neither automatic rejection nor a policy-version snapshot exists.

## 5. Threshold fitness and range analysis

### Source-derived range

For an applicant with both profile and contact, currently live historical helpers return no records. The high source-derived advanced combination is:

```text
base max 0.64 * 0.40       = 0.2560
geography max 0.21 * 0.15 = 0.0315
fraud is clamped at 1.00 * 0.20 = 0.2000
history currently 0.00 * 0.25 = 0.0000
advanced maximum before rounding          = 0.4875
legacy maximum after clamp                = 1.0000
combined maximum                          = 0.5900–0.5904
```

The slight range reflects Python rounding/floating representation: the executed maximum profile returned `advanced=0.487`, `legacy=1.000`, `combined=0.5896`. Even the upper bound is far below `0.95`. If profile/contact are missing, the history fallback is `0.10`, but base/fraud/geographic potential is lower; it does not make the threshold reachable.

### Boundary check — executed synthetic evaluation

| Input combined score | Current eligible result | Evidence |
| ---: | --- | --- |
| `0.949` | `True` | Direct call to `_is_eligible_for_enhanced_auto_approval`. |
| `0.950` | `False` | Direct call; strict operator confirmed. |
| `0.951` | `False` | Direct call. |

**Conclusion:** `< 0.95` is syntactically precise but not a meaningful live score discriminator. In the inspected code, manual review from a real evaluation is triggered by hard blockers, not score magnitude. The threshold must not be represented as a calibrated security threshold without calibration evidence.

## 9. Seven hard-blocker fitness

| Blocker | Generation source / exact trigger | Current fit and risks | Requirement support |
| --- | --- | --- | --- |
| `temporary_email_domain` | Fraud service adds it when email contains `tempmail`, `10minutemail`, `guerrillamail`, or `mailinator`. | Plausible abuse signal, but substring matching can catch unrelated domains/local parts; not authoritative verification. | `test_contact_name` | Same test-pattern substring in contact name. | Same false-positive risk; manual review available. | Exact rule unratified. |
| `high_failure_rate_domain` | Historical helper emits when same-domain rejected/suspended rate >30%. | Desired signal concept, but helper returns `[]` today; no live source of truth or calibration. | `EVIDENCE_NOT_FOUND` for live behavior. |
| `multiple_recent_applications` | Historical helper emits when >1 recent application for contact. | Desired anti-abuse concept, but currently unreachable without mocking; needs defined window/identity matching/false-positive handling. | `EVIDENCE_NOT_FOUND` for live behavior. |

All seven trigger through substring membership against controlled factor strings. Known generated strings align with the blocker substrings, so no separate factor currently causes an accidental hard block by name. The design is nevertheless brittle: the policy boundary is string coupling rather than typed factor codes, and factor ordering is nondeterministic because of `list(set(...))`. This affects audit reproducibility/display order, though membership-based eligibility is stable for the same set.

## 10. Dual-evaluation consistency

The command evaluates risk before persistence with `application_id=None`, embeds that result in internal application JSON, then evaluates again after transition to pending review using the persisted application ID. For the executed ordinary scenario, both evaluations returned `0.0144`, eligible, and equal factor sets because the live history helper methods return empty lists and do not use the application ID.

This is **not** a proof of future consistency. If the history methods are later wired to persistence, the second evaluation can see the newly created application or other concurrent applications, changing history score/factors and potentially the decision. A one-time, versioned policy snapshot at the approved decision point is the minimum reproducibility correction; it does not require a policy-management platform.

## 11. PF-018 and professional-validation reconciliation

### Verified contact

Current automatic approval must not be retained without PF-018 evidence. The smallest compliant policy choices are:

| Choice | Security | Applicant friction | Recommendation |
| --- | --- | --- | --- |
| Both explicitly submitted email and mobile must exact-match authoritative confirmed evidence | Strongest where both contacts are collected; aligns PF-018’s independent-evidence rule. | Requires both confirmation journeys before automation. | Preferred if both are kept as mandatory clinic contacts in registration. |
| One applicant-designated submitted contact must exact-match | Strong, minimal initial friction. | Requires explicit designation and clear verification UI. | Acceptable only if owner formally makes the other contact optional for automatic approval. |
| Caller/profile/login supplies verification | Not secure or PF-018 compliant. | Low friction but invalid. | Reject. |

### Registration versus professional eligibility

An organization owner/clinic administrator is not necessarily a registered medical practitioner. US-1.2 requires registration/professional validation but does not say that every public organization registrant must personally be a clinician. Owner must decide which evidence belongs to organization registration (e.g., clinic/business registration) and which belongs later to clinical-staff activation. Until then, missing registration cannot be silently treated as a harmless score increment for automatic approval.

## 12. Applicant UX implications

The intended journey is low cognitive load: registration -> safe automatic decision or clear review/verification need -> workspace preparation -> setup/resume. Current issues:

- automatic `onboarding` response is displayed as pending review because mobile checks only `APPROVED`;
- public response exposes score/factors/reason that applicants should not need or receive;
- verification-required is not represented in the current public journey;
- provisioning recovery falls to a generic no-clinic state rather than safe continuation guidance;
- form headings/labels are static English while error/status paths use localization; English/Hindi and accessibility interaction evidence is missing.

No real conversion percentage is asserted. Scenario results show low scoring friction today, but PF-018 verification will add intentional friction that must be clear, resumable, localized, and no more demanding than the ratified contact rule.
