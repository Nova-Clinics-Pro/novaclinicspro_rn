## Verified identity and cache lifecycle

The reactive verified identity is `useAuthStore(...).currentUser.userId`, guarded by `isAuthenticated`. `AuthSessionService` updates this Zustand state during login, bootstrap, refresh, and authentication-state changes. The hook subscribes to that store selector, so an identity change re-renders its query observer.

Current path:

`AuthSessionService` → `useAuthStore.currentUser.userId` → `useRegistrationStatus` → TanStack Query identity-scoped key → `GetRegistrationStatusUseCase` → registration repository → `GET /registration-status/me`.

`UnifiedLogoutService` already clears the shared query client on explicit logout. This remains preserved, but the correction does not rely on logout clearing for account switching. No registration-status cache persistence/hydration, `placeholderData`, `initialData`, or previous-data option was found in this hook path.

## Defect and correction

Immediately before FIX-02, the in-progress CS-002 hook used one shared authenticated-applicant key. A same-QueryClient characterization test failed before the correction: after replacing applicant A with applicant B, the hook did not issue B's distinct status request (`expected 2 calls; received 1`). This proved the unsafe shared identity boundary.

`frontend/features/registration/presentation/hooks/useRegistrationStatus.ts` now:

- obtains the verified user ID reactively from the existing auth store;
- uses `['registration-status', 'authenticated-applicant', authenticatedUserId]` as its key;
- disables the query when no verified authenticated identity exists; and
- keeps the existing `/registration-status/me` use-case/repository boundary.

The key contains neither bearer/session material, a route parameter, an application ID, nor a tenant ID. The stable user ID means a same-user token refresh retains the same cache identity.

## Security-negative behavior tested

`frontend/tests/registration/b27RegistrationStatusIdentityCache.test.tsx` uses the real hook, real auth Zustand store, one persistent `QueryClient`, and deterministic deferred API responses. It verifies:

- A's approved continuation becomes visible to A, but is absent immediately after A → B without logout while B is pending.
- An in-flight A response that resolves after A → B populates only A's key; B's active observer remains empty until B's response resolves.
- A failed B status request does not revive or expose A's cached continuation.
- Same-user refresh does not refetch or discard the valid cache entry.
- Unauthenticated transition disables the query and exposes no prior continuation; a later B authentication fetches B's status under B's distinct key.
- Distinct authenticated identities produce distinct keys with only the user ID as identity material.

Together with `tests/onboarding/ChoiceScreen.clinic-entry.test.tsx`, this prevents an untrusted route application ID or an A-scoped continuation from being used by B's Choice path. Backend ownership remains the authority of the existing `/registration-status/me` and application-detail authorization contracts; no backend change was made.
