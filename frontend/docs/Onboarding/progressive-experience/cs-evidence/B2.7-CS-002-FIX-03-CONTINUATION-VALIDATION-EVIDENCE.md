## Defect reproduction and root cause

Before the correction, the focused resolver test passed this malformed runtime payload:

```ts
{
  status: 'approved',
  continuation: { kind: 'approved_choice' },
}
```

Expected route: `null`. Actual route: `/onboarding/choice`.

The root cause was a truthiness check on `status.continuation` in `resolveRegistrationStatusRoute()`. TypeScript interface declarations did not validate untrusted external data at runtime.

## Validation design and production change

`frontend/features/registration/presentation/registrationStatusRouting.ts` now contains a private, pure `isApprovedChoiceContinuation()` guard. It accepts only a non-array object with:

1. `kind === 'approved_choice'`;
2. a UUID-formatted `application_id`; and
3. a `tenant_name` that remains nonempty after trimming for validation.

The guard does not normalize or mutate data, navigate, access authentication state, or create an ownership authority. It uses a local standard UUID pattern because this frontend contains no canonical UUID-validation helper. The resolver still returns only its existing safe routes and does not inject application identifiers into any route.
