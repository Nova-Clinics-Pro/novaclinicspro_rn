## 1. Executive decision

FIX-05 eliminates the original source-level direct-entry defect: `ChoiceScreen` no longer derives an application ID merely from `kind`, and it cannot enable its detail hook unless the status is `approved`, a verified authenticated identity is present, and the canonical continuation validator succeeds.

The original finding is not fully closed because the current ChoiceScreen test replaces `useApplicationDetailQuery` with a test double. It proves the screen supplies `enabled: false` and its simulated enabled query function is not called; it does **not** execute the real TanStack Query hook through its mocked datasource. The hook's source indicates disabled queries should not execute, but that remains source-level reasoning rather than direct network-path execution evidence.

No security defect remains demonstrated by current source or tests. CS-002 remains unclosed because real query-to-datasource, frontend/backend API, and database-backed ownership acceptance evidence is still absent.

## 5. Canonical validator consistency

`frontend/features/registration/presentation/registrationStatusRouting.ts:isApprovedChoiceContinuation` is the single validator used by both root routing and ChoiceScreen. It rejects null, arrays, nonobjects, wrong kind, nonstring/malformed UUIDs, and blank tenant names. Root routing invokes it only for `status === 'approved'`; ChoiceScreen applies the same status condition before invoking it.

No duplicate Choice-specific validator, permissive fallback ID, TypeScript suppression, DTO widening, or route-controlled ID path was found.

## 6. Query-enablement and network-path findings

`ChoiceScreen` passes `applicationId || ''` and `{ enabled: Boolean(applicationId) }` to `useApplicationDetailQuery`. The hook builds its TanStack query with `queryFn: () => getApplicationDetailApi(applicationId)`, `enabled: !!applicationId`, then spreads caller options; Choice's explicit `false` therefore remains false.

There is no alternate effect, callback, or route parameter path that calls `getApplicationDetailApi`. Source therefore supports that invalid continuation does not initiate the fetch. However, this was not directly exercised with the **real** `useApplicationDetailQuery` and mocked `getApplicationDetailApi`; current ChoiceScreen tests mock the hook itself. The network-path invariant is **partially verified**, not fully verified.

## 7. Direct-entry coverage

`frontend/tests/onboarding/ChoiceScreen.clinic-entry.test.tsx` mounts ChoiceScreen and covers:

- missing, null, empty, wrong-kind, missing-ID, empty-ID, malformed-UUID, missing-tenant, and blank-tenant continuations;
- a nonapproved status with valid-looking continuation;
- unauthenticated identity;
- loading and failed status resolution;
- attacker-supplied route ID;

For invalid inputs the test asserts an empty ID and disabled hook, no onboarding application-ID initialization, and no simulated enabled detail-query function invocation. The valid case asserts the canonical UUID is used and the simulated enabled query function receives it. This is mounted presentation evidence, not actual datasource integration evidence.

## 8. Identity isolation

FIX-02's real shared-QueryClient test (`b27RegistrationStatusIdentityCache.test.tsx`) verifies the identity-scoped key `['registration-status', 'authenticated-applicant', authenticatedUserId]`, A→B cache separation, late-A response isolation, B failure isolation, same-user token-refresh continuity, and unauthenticated disablement. The test does not mount ChoiceScreen across a full auth-store identity transition, so that exact composed journey remains integration evidence pending. No cross-identity leak was found in current source or executed unit coverage.

## 9. Backend authorization review

`self_registration_router.py:get_my_registration_status` requires `CurrentUser` and passes only its verified `user_id` into `ApplicantRegistrationStatusService`. `SQLAlchemyApplicantRegistrationStatusRepository.get_for_authenticated_applicant` joins creator `OrgUser`, filters on `OrgUser.auth_user_id`, and deterministically selects latest `created_at DESC, id DESC` record. Continuation is created only when the projected state is approved and contains application ID plus tenant name, not tenant ID, roles, permissions, reviewer, or risk data.

`applications_router.py:get_my_tenant_application` requires authenticated `UserContext`; `ApplicationsService.get_my_application` receives the caller identity and independently checks application ownership. `/auth/me` derives effective tenant context via `AuthenticatedOrganizationContextService`, so registration continuation is not tenant authority.

Backend execution is unverified in this environment: neither `venv/bin/pytest` nor `.venv/bin/pytest` exists. No backend success is inferred from historical reports.
