**Task:** B2.7-CS-006

**Mode:** read-only source and existing-evidence audit
**Decision:** `BLOCKED_SECURITY_DEFECT`

## 1. Executive decision

The accumulated CS-002 work establishes important safeguards: the status endpoint is authenticated and applicant-scoped; the continuation intentionally excludes tenant identifiers and permissions; the root route validates an approved continuation structurally; and the registration-status cache is keyed by authenticated applicant identity.

It is **not acceptance-ready**. `ChoiceScreen` can be reached directly and treats every authenticated continuation whose `kind` is `approved_choice` as queryable. It does not repeat the root gate's UUID and nonblank-tenant-name validation. Consequently a malformed continuation can cause an application-detail HTTP request, contrary to Journey G's required “no untrusted application-detail query” invariant. Backend ownership checks mitigate disclosure, but do not make the frontend trust-boundary breach acceptable.

No code, test, configuration, database, or Git-history changes were made by this audit. This document is the sole task-owned artifact.

## 7. Backend ownership and authorization review

`self_registration_router.py:get_my_registration_status` receives identity only from verified `CurrentUser`, passes `current_user.user_id` to `ApplicantRegistrationStatusService.get_for_authenticated_applicant`, and does not accept a caller-chosen applicant ID. `SQLAlchemyApplicantRegistrationStatusRepository.get_for_authenticated_applicant` joins application creator `OrgUser`, filters `OrgUser.auth_user_id == str(auth_user_id)`, orders newest application by `created_at DESC, id DESC`, and limits one.

The implementation is deterministic. It returns a continuation only after application-status/recovery projection yields approved. The selected row is projected as provisioning-completed when a recovery tenant exists or recovery succeeded; otherwise the latest record governs. The audit did not find a requirement proving that an older approved record must supersede a newer pending/rejected record, so this is recorded as current behavior rather than a defect.

`applications_router.py` delegates application detail to `ApplicationsService.get_my_application(application_id, current_user.user_id)`. The service resolves the authenticated user's organization user and rejects a record whose `created_by` differs. Thus a foreign application ID is independently ownership-protected. The continuation omits tenant ID, roles, permissions, reviewer data, and risk score. This is source-reviewed only; no database-backed enumeration/error-disclosure test was executed.

## 8. Tenant authority and identity isolation

`auth_router.py:get_current_user_info` derives effective tenant context through `AuthenticatedOrganizationContextService` and emits it in `/auth/me`; it is the authority used by the root route. Registration status only informs applicant presentation and does not create tenant context. `ChoiceScreen` supplies only an application ID to application detail; it does not derive a tenant ID from route params or continuation. The lifecycle contract confirms that approved application status is not tenant authorization.

The identity cache implementation is meaningful rather than a query-key-string-only check: the identity-cache test uses an actual shared QueryClient, changes identities, and controls in-flight promises. It covers A→B cache separation, in-flight isolation, failure isolation, same-user refresh, and disabled unauthenticated use. It does not prove server-session invalidation or a device/network end-to-end logout race.

## 9. Automatic-approval-first preservation

CS-002 reads status and projects an existing approved continuation. It does not implement approval eligibility, validators, thresholds, risk scoring, reviewer decisions, or provisioning policy. Source reviewed supports preservation. Full frozen-policy conformance cannot be proven because the named MVP-ONB-003 source was unavailable in these worktrees.

## 10. Clean Architecture assessment

The frontend continuation path follows presentation (`useRegistrationStatus` / root or Choice) → use case → repository → datasource → Axios HTTP. `ChoiceScreen` uses the existing repository-owned TanStack Query hook and does not import Axios. The backend path is router → factory → application service → repository port/UoW → SQLAlchemy adapter. The application service has no ORM/session dependency.

The direct-Choice structural validation omission is a security/consumer-boundary defect, not a persistence-layer architecture bypass. No other CS-002-specific dependency-direction violation was found.
